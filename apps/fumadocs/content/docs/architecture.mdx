## Application stack

| Concern         | Decision                                                        | Why it matters                                                                                                                             |
| --------------- | --------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| Web application | Next.js 16 App Router and React 19                              | Server Components keep financial queries on the server while authenticated route handlers provide explicit mutation and import boundaries. |
| Interface       | Tailwind CSS, shadcn/ui New York styling and EvilCharts/ECharts | A consistent dashboard-01 visual system with responsive, interactive financial visualizations.                                             |
| Database        | Neon Postgres                                                   | Durable relational storage, managed backups and connection pooling suitable for Vercel's serverless runtime.                               |
| Data access     | Drizzle ORM with tracked SQL migrations                         | Typed queries plus reviewable schema changes and database-enforced ownership relationships.                                                |
| Authentication  | Better Auth                                                     | Google OAuth, email/password authentication, rolling database sessions, secure production cookies and database-backed rate limiting.       |
| Repository      | pnpm workspaces and Turborepo                                   | Keeps the web app, API logic, authentication, database, environment validation, UI and documentation in independently checkable packages.  |
| Documentation   | Fumadocs                                                        | Versioned product and engineering documentation stored beside the implementation.                                                          |

## Package boundaries

```text
apps/web        Authenticated Next.js product
apps/fumadocs   Product and engineering handbook
packages/api    Server-only queries, imports and mutations
packages/auth   Better Auth configuration
packages/db     Drizzle schema and SQL migrations
packages/env    Runtime environment validation
packages/ui     Shared shadcn/ui components and tokens
```

The portfolio query and mutation modules import `server-only`, preventing accidental use in client bundles. Browser components submit to authenticated route handlers, and those handlers derive the owner from the server session rather than accepting a user ID from the request.

The application can be published as source code. Personal workbooks, broker exports, environment files and portfolio values are intentionally excluded from the repository.

## Deliberate trade-offs

- Postgres is the source of truth; no portfolio defaults or hardcoded user data are used as fallbacks.
- Financial history is normalized into identities, dated snapshots, import batches and ledger entries. This costs more storage than overwriting values but preserves auditability.
- Real estate has a dedicated model because its area, ownership and legal attributes do not fit a generic asset record cleanly.
- Commodity valuation and physical inventory use separate linked models: the holding owns the declared total, while item snapshots preserve provenance and reconciliation detail without duplicating portfolio value.
- Household planning has a dedicated model because recurring costs, refunds, contract terms and one-time purchases have different history and calculation rules.
- Broker imports are provider-specific at the parsing boundary and normalized after parsing. Adding another broker should introduce a parser, not a second portfolio model.
- Broker-ledger queries are provider-scoped. Zerodha tradebook entries cannot enter Degiro holdings or analytics even though both use the shared normalized ledger.
- Payslip parsing is adapter-based and currently verifies the supplied euHReka layout. Unsupported layouts fail explicitly instead of guessing financial values.
- FIRE calculations are implemented as a pure, deterministic engine. Database queries normalize every included amount into the user's base currency before calling it, and missing FX rates are disclosed rather than replaced with guessed values.
- The expected annual path and Monte Carlo range are deliberately separate. Reproducible seeded simulations make results testable while still communicating sequence-of-returns and inflation risk.
- Analytics are aggregated from account-scoped Postgres queries and rendered with ECharts in the browser. DuckDB-Wasm is intentionally deferred: current datasets are small enough that another browser database, worker and duplicated data transfer would add more complexity than speed. It becomes relevant only for large, local, ad-hoc statement analysis.
- Deployment migrations are separate from the web runtime. The application receives only a pooled connection string; a direct database credential is reserved for trusted migration execution.
