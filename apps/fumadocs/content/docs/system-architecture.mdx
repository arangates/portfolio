## Primary request and data path

The emphasized path is the normal financial import flow:

1. A signed-in user selects an XLSX, CSV or PDF export in the browser.
2. A Next.js route handler verifies the Better Auth server session.
3. The handler passes the session-derived `userId` and file bytes to `@portfolio/api`.
4. A provider-specific adapter parses the file into normalized records.
5. Drizzle writes owner-scoped rows, snapshots and import evidence to Neon Postgres.

Reads take the reverse server-side route. Analytics and FIRE calculations operate on account-scoped database records, disclose missing FX conversions and return derived series for tables and ECharts visualizations.

## Trust and ownership boundaries

| Boundary                     | Responsibility                                                                                                                       |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| External providers and files | Google supplies identity; broker and payroll exports remain user-controlled until explicitly selected.                               |
| Vercel application           | Next.js owns request routing, protected layouts and authenticated API endpoints.                                                     |
| Authenticated account        | Better Auth establishes the session. Clients do not submit or choose the financial-data owner.                                       |
| Managed data                 | Neon is the source of truth. Financial tables carry `user_id`, and composite foreign keys keep related history under the same owner. |

The deployed web runtime receives the pooled `DATABASE_URL` and application secrets. Direct database credentials stay outside the application and are reserved for trusted migrations.

## Historical integrity

Imports are additive and auditable rather than destructive. SHA-256 file and row hashes make repeat uploads idempotent, while import batches, normalized ledger entries and dated snapshots preserve provenance and history. Raw imported content is retained with its batch so a normalized result can be traced back to the supplied source.
