description: The controls protecting portfolio data and deployment secrets.

## User isolation

Every portfolio, salary, household and FIRE table carries a required owner ID linked to the authentication user. Server-side queries, mutations, imports, exports and archival operations use the user ID from the verified session. The client cannot select or override the owner.

## Authentication controls

- Google OAuth and email/password authentication with a 12-character minimum password.
- One-year rolling, database-backed sessions with secure cookies in production.
- Database-backed authentication rate limiting.
- Explicit canonical authentication URL and trusted browser origin.
- Account deletion support through Better Auth.

## Sensitive-data handling

- Bank records accept only a safe label and optional last four digits—never full account numbers or credentials.
- Salary PDFs are parsed in memory. The database stores a file hash and normalized financial rows, but not the PDF, extracted text, home address, birth date, payroll number or bank account.
- ITR JSON is parsed in memory and discarded. The application stores normalized tax totals, filing metadata and a fingerprint, but not the raw JSON, PAN, address, bank details or verification payload. UI queries expose only the last four acknowledgement digits.
- Household imports omit service client numbers and login identifiers. Contracts retain only the provider, service, financial terms and non-sensitive operational notes needed for planning.
- Metals imports store normalized inventory and an audit fingerprint, not the source CSV. Source remarks are treated as provenance and never interpreted as account ownership.
- Broker files and personal workbook values are data, not source code, and must never be committed to Git.
- Tradebook rows and source files are linked to the authenticated account. Import requests never accept a user ID from the browser, and cross-provider analytics explicitly filter the broker source.
- Family names, dates of birth, income, expenses and retirement assumptions are private account data. They are stored only in Postgres and never embedded as product defaults or source code.
- Production secrets live in Vercel environment variables; local secrets live in ignored `.env` files.
- Google OAuth client secrets are server-only and never exposed through `NEXT_PUBLIC_` variables.
- The web runtime uses Neon's pooled `DATABASE_URL`. The direct connection credential is reserved for trusted migration execution and is not configured in the deployed application.
- Private exports use authenticated, non-cacheable responses.

## Operational rules

1. Rotate a credential immediately if it appears in a screenshot, log, commit or chat.
2. Use separate Neon branches and secrets for Preview and Production.
3. Never point untrusted preview code at production portfolio data.
4. Apply and review tracked migrations before deploying code that depends on them.
5. Run dependency audit, type checks, linting and a production build before release.

Security headers, upload size limits, validated input schemas and server-only data modules provide additional defence in depth. Database ownership constraints remain the final boundary for relational integrity.
