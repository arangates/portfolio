## Historical model

Records that change over time are divided into two parts:

1. An **identity record** stores stable attributes, such as a bank-account label, deposit institution, commodity name or property address.
2. A **snapshot record** stores dated financial state, such as balance, principal, quantity, price or valuation.

Editing an item updates appropriate identity metadata and inserts a new snapshot. Earlier snapshots remain available for analytics and audit. Archiving marks the identity inactive; it does not delete history.

## Broker imports

Each import creates an account-owned batch containing the source, file hash, statement date, status and row statistics. Raw source rows and normalized records are linked to that batch.

### Zerodha

A holdings workbook becomes a complete dated position snapshot. Re-uploading the identical file returns the existing batch because uniqueness is enforced by user, import type and file hash.

### Degiro

Transactions and Account exports become a chronological ledger. Stable row hashes and account-scoped entry keys prevent duplicates across overlapping exports. Holdings and moving-average cost are reconstructed from all retained buy and sell entries, rather than from only the newest file.

## Salary PDF imports

Salary imports use a separate account-owned model: a file fingerprint records processing provenance, a payslip record stores normalized monthly totals, and line items preserve the financial breakdown. Exact file duplicates are ignored. If payroll issues a changed PDF for the same month, both revisions remain in history and the latest successful revision drives current analytics.

The browser queues each selected PDF as an individual authenticated request. This allows a 50-file selection without creating one oversized Vercel request, and makes partial failures retryable without reprocessing successful files.

## FIRE planning records

FIRE assumptions, family members, recurring expenses, one-time costs, income streams and scenarios are stored as separate account-owned records. Calculated corpus values and simulations are not stored as facts; they are recomputed from current source records, portfolio liquidity and stored FX rates.

Archiving an expense, goal, income stream or family member removes it from future projections without deleting the audit event. The JSON export includes the underlying FIRE records so the plan is portable and independently auditable.

The guarded FIRE workbook importer is repeatable for the same account and workbook identities. Always run the dry-run first:

```bash
pnpm db:import-fire-workbook -- \
  --email=user@example.com \
  --file=/absolute/path/to/FIRE.xlsx
```

Execution additionally requires `--execute`, the same `--confirm-email`, and the exact `--expect-host` printed by the dry-run. The importer updates matching FIRE records, validates expense and one-time-cost totals, stores no raw workbook and does not duplicate the account owner's linked portfolio assets.

## Household records

Recurring budget items and service contracts have stable identity rows plus effective-dated snapshots. Updating an amount or contract term preserves the earlier value. Scenarios and one-time purchases are independent records, so a car or house-setup purchase never inflates the monthly run rate.

The guarded household workbook importer uses every valid row in the detailed monthly sheet and independently reconciles gross expenses, refunds and net cost. It does not trust stale summary formulas. Run the dry-run first:

```bash
pnpm db:import-household-workbook -- \
  --email=user@example.com \
  --file=/absolute/path/to/Housing.xlsx
```

Execution additionally requires `--execute`, the matching `--confirm-email`, and the exact `--expect-host` printed by the dry-run. Stable source keys make repeat execution idempotent. The importer stores normalized financial records and an audit summary, but not the source workbook, client numbers, login identifiers or other credentials.

## One-time legacy workbook migration

The repository includes a guarded local command for migrating cash accounts, fixed deposits, commodities, real estate, manual assets and a dated FX rate from the supported legacy workbook layout. It is intentionally separate from the browser importer because the workbook may contain credentials alongside portfolio data.

Run a dry-run first:

```bash
pnpm db:import-legacy-workbook -- \
  --email=user@example.com \
  --file=/absolute/path/to/workbook.xlsx
```

The dry-run reconciles category totals, displays the exact database host and changes no rows. Execution additionally requires `--execute`, the same email in `--confirm-email`, and the exact `--expect-host` value printed by the dry-run.

The migration is idempotent for the same user, workbook and as-of date. It stores masked account suffixes and financial records, but never stores the raw workbook, passwords, PINs, login IDs, full account numbers, CIFs or card data. Existing broker imports remain authoritative and are not duplicated from derived workbook tabs.

## Ownership enforcement

Ownership is enforced twice:

- Application queries always filter by the authenticated session user.
- Composite database foreign keys require child snapshots, batches and ledger rows to have the same `user_id` as their parent record.

This prevents an application error from linking one user's snapshot or imported row to another user's portfolio object.

## Calculation rules

- Portfolio totals use the latest snapshot for each current record.
- Ownership-based assets use attributable value: full market value multiplied by ownership share.
- Multi-currency totals use stored dated FX rates. Missing conversions are disclosed and excluded.
- FIRE corpus calculations use investable assets rather than total net worth, account for time-bounded expenses and income, and apply one-time costs in their planned year.
- Household totals calculate refunds separately and subtract them once at household level before computing a per-adult share.
- Indian-equity performance uses values supplied by the latest Zerodha snapshot.
- Global-equity open cost and realized results use moving-average cost. Estimated market value uses the most recent imported trade price.

These calculations are informational. They are not a substitute for broker statements, audited accounting or tax records.
